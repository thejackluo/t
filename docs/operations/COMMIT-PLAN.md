## Staging and review procedure

For each row, stage only its listed paths, inspect the result, then make the requested commit. Example for the first row:

```sh
git status --short
git remote -v
git ls-remote --heads origin
git log --oneline -10
git diff
git add -- .gitignore AGENTS.md README.md docs/README.md docs/INTERACTIVE-MAP-PLAN.md docs/references docs/operations docs/GUINNESS-RULES.md
git diff --cached --name-status
git diff --cached --check
git diff --cached
git commit -m "docs: define repository structure and rule references"
```

The remaining staging commands, each followed by the same staged-diff review and its table's commit message, are:

```sh
git add -- backend
git add -- utilities
git add -- frontend
git add -- docs/archive
```

These are four separate staging/commit cycles, not one combined staging batch. Avoid `git add .`. If additional commits already exist when this plan is executed, review `git diff` and stage any corresponding old-path deletions as well.

Keep `.opencode/`, Python environments/caches, downloaded feeds, `output/`, credentials, and attempt evidence out of every commit. The old `.planning` symlink is retired, not an item to stage. Publishing to GitHub is a later explicitly requested action.
